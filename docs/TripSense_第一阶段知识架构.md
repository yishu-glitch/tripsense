# TripSense 第一阶段知识架构（上海 MVP）

## 1. 阶段目标

第一阶段不追求“模型什么都知道”，而是让系统能够区分知识类型、选择正确的数据通路，并明确告诉用户哪些结论可靠、哪些仍未知。

本阶段交付一条可离线运行的上海规划链路：

1. 本地意图解析得到时间、节奏、场景和偏好。
2. 结构化库负责硬筛选与基础属性。
3. 稳定知识库负责召回文化、建筑和体验语义。
4. 实时工具接口负责天气、开放、拥挤、预约和交通状态。
5. 规划器在安全时间预算内组合路线，并随每个点返回证据。

## 2. 三层知识及职责

| 知识层 | 负责内容 | 当前实现 | 失败时行为 |
|---|---|---|---|
| 稳定知识 RAG | 历史、文化、建筑、体验特征、适合人群 | 上海编辑种子库 + 中文词法检索；接口可替换为向量检索 | 没有证据就不生成稳定知识结论 |
| 结构化状态 | 坐标、行政区、类别、评分、距离、营业时间字段 | CSV 仓储 + 距离图 + 经纬度兜底 | 脏营业时间标记为未验证，不把商圈名当营业时间 |
| 实时工具 | 天气、开放、拥挤、预约、交通 | `RealtimeProvider` 工具协议、不可用兜底、静态开发适配器 | 明确返回 `unknown`，绝不由大模型补写实时事实 |

## 3. AI 与规则的边界

AI 更适合处理语义和软偏好：

- 理解“慢慢走”“想看真实的街区生活”等自然语言。
- 从稳定知识中召回与用户语义匹配的地点和体验证据。
- 后续可用于生成自然、个性化但有证据约束的解释。

规则与算法负责可验证的约束：

- 城市、类别、黑名单和实时关闭状态等硬筛选。
- 路线时间、点间移动、停留时长及安全预算。
- 二机会约束控制超时风险；卡尔曼滤波后续用于根据实际行程持续校准时间估计。
- 实时数据过期、不可用或不确定时的降级策略。

推荐分数是“可解释软排序”，不能越过硬约束。当前基线由热度、评分、场景属性、RAG 匹配和实时修正共同组成。

## 4. 数据契约

每个候选点统一为 `CandidateContext`，包含：

- `poi`：结构化 POI。
- `stable_document`：命中的稳定知识文档，可为空。
- `realtime_state`：实时状态；未接入时各字段为 `unknown`。
- `evidence`：结构化、RAG、实时三类证据及新鲜度。
- `score`：软排序分数。
- `excluded_reason`：实时关闭或预约不可用等硬排除原因。

证据的新鲜度分为：`stable`、`fresh`、`stale`、`unknown`。前端应直接展示未知或未验证状态，不能隐藏为肯定描述。

## 5. 当前 API

### 路线规划

`POST /api/v1/routes/plan`

```json
{
  "city": "shanghai",
  "text": "今天想慢慢走，看看老建筑和真实的街区生活，大概四小时"
}
```

每个路线点返回 `reason`、`evidence` 和 `realtime_status`。

### 知识检索调试

`POST /api/v1/knowledge/search`

```json
{
  "city": "shanghai",
  "text": "想慢慢走，看看老建筑和街区生活",
  "limit": 10
}
```

该接口返回进入路线优化前的候选点，可用于前端解释、检索评估和数据质检。

## 6. 当前完成边界

已完成：

- 三层知识统一契约及编排器。
- 上海稳定知识种子和可替换的检索边界。
- 上海结构化 POI 过滤、数据质量标记和距离兜底。
- 实时工具协议、显式未知降级及关闭/预约/拥挤/交通修正规则。
- 路线结果携带逐点证据。
- 自动化测试覆盖数据质量、RAG 匹配、实时排除和服务输出。

尚未声称完成：

- 真实天气、交通、预约和拥挤数据源的生产接入。
- 向量数据库、重排模型及大规模知识库。
- 营业时间的可信来源核验与日期化计算。
- 用户长期画像和行程中动态重规划。

## 7. 下一迭代验收标准

1. 接入至少一个真实天气工具和一个交通工具，并保留超时、过期和不可用降级。
2. 建立 30—50 条上海典型查询集，评估候选召回、路线相关性和解释可信度。
3. 扩充稳定知识库并记录来源、版本和更新时间。
4. 任何涉及“当前开放、是否拥挤、能否预约、交通是否正常”的表达都必须有新鲜实时证据，否则只能说未知。

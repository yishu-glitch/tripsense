## 1. 指标框架

TripSense 的产品闭环是：

```text
开始规划 → 形成路线 → 保存采纳 → 回访/继续对话 → 添加旅行记录
```

北极星方向为「被用户持续使用的有效行程」。MVP 阶段拆成三组可观测指标，避免用单一数字过早概括：

| 组别 | 回答的问题 |
|------|------------|
| 规划采纳 | 用户有没有把路线当真、愿意保存？ |
| 保存后持续使用 | 保存之后还会不会回来用？ |
| 质量护栏（含离线 Eval-200） | 路线是否可靠、改线后硬要求是否还在？ |

---

## 2. 规划采纳指标

### 2.1 AI 规划保存转化率

保存至少一份行程的规划用户数 / 进入个性化规划的用户数。

需区分灵感进入、首页 AI 进入和从旧行程继续对话三种来源。

### 2.2 首次保存对话轮数

统计开始规划至首次保存之间的有效用户输入轮数，观察中位数、P75、P90 和分布。过多可能表示理解或决策成本高；过少也可能意味着用户未充分理解路线，因此必须与保存率、后续打开和主观满意度联合判断。

### 2.3 调整后保存率

发生时间、地点、日期或主题调整的会话中，最终保存更新版本的比例。同步记录撤销率、重新生成率和直接退出率。

---

## 3. 保存后持续使用指标

- **7 日/30 日行程打开率**：保存后相应周期内至少再次打开一次的行程比例；
- **每份行程打开频率**：观察均值与分布，区分本人浏览和分享访问；
- **从已保存行程再次发起对话率**：打开保存行程后，以该行程为上下文发起 AI 对话的比例；
- **行程再次编辑率**：保存后再次调整日期、地点、时间或每日主题的比例；
- **提醒使用率**：预约、开放、天气等提醒的展开、跳转或确认比例。

---

## 4. 旅行记录指标

- **记录转化率**：已保存行程中，至少产生一条文字、心情或照片记录的比例；
- **照片记录转化率**与**文字记录转化率**分别统计；
- **记录深度**：产生记录的行程平均记录地点数、记录条数和跨天数；
- **计划外地点记录率**：存在新增实际地点记录的行程比例；
- **记录后回访率**：产生记录后再次打开手账或行程的比例。

这些指标反映「攻略是否长成记录」，但不应被设计成打卡任务。

---

## 5. 质量护栏

### 5.1 路线可靠性

- 闭馆、预约和营业时间硬冲突率；
- 距离或交通明显不合理率；
- 无效 POI、重复 POI 和普通门店误推荐率；
- 父子地点重复进入同一路线的比例；
- 实时信息过期或无来源比例。

### 5.2 AI 质量

- 当前行程、日期和地点识别正确率；
- 多轮约束保留率；
- 答非所问率；
- 未经确认修改行程率；
- 推荐理由事实一致性与证据覆盖率；
- 需要澄清却直接生成方案的比例。

### 5.3 交互与信任

- 登录弹窗后的继续率与流失率；
- 时间编辑完成率、放弃率和撤销率；
- 路线侧栏打开率及返回对话后的继续率；
- 照片权限授权率、拒绝率和撤回率；
- 用户对「路线太满、太松、像模板、解释机械」等反馈占比。

## 6. 事件埋点建议

至少记录：

```text
destination_selected
inspiration_viewed / inspiration_selected
planning_chat_started
route_draft_generated
route_panel_opened
stay_time_edited
route_change_proposed / confirmed / rejected / undone
trip_saved / trip_version_saved
saved_trip_opened
chat_started_from_saved_trip
reminder_viewed / reminder_action_clicked
note_added / photo_added / unplanned_place_added
```

关键事件携带匿名用户、城市、行程、路线版本、日期索引、来源入口、模型版本、策略版本与时间戳。不得在分析事件中写入照片正文、精确位置或完整对话等不必要敏感内容。

## 7. 离线评测：Eval-200 对话集

离线评测回答的是：**在固定对话金标准上，规划器给出的路线是否可靠、改线后是否仍合理**。它不证明真实用户价值，也不把「唯一标准路线」当金答案。

- 数据集：`data/eval/dialogue_eval_200.jsonl`（从约 800 条模拟多轮中分层抽取）
- 筛选说明：`data/eval/SELECTION_REPORT.md`
- 跑批报告：`data/eval/reports/`（含 `multi_turn_summary_*.md`）

### 7.1 评什么：首轮 vs 多轮

| 模式 | 产品含义 | 读摘要时看 |
|------|----------|------------|
| **首轮** | 只用用户第一句做初始规划，看「第一次给出来的路线」好不好 | 表中「首轮」行；「调整合理性」通常为「—」（还没有改线可评） |
| **多轮** | 按整段对话依次改线，看**改完后的最终路线** | 表中「多轮」行；更能暴露「太满了缩短」「再加点」「换天气」后的回退 |

二者是**两次独立跑批**，不是同一次执行里的前后阶段。「本轮 / 修复前」只是人工贴的对比标签，方便看改动前后差异。

### 7.2 六项质量量纲（产品语言）

每条用例会得到六项 0–1 分，再合成一个综合分。**单项 pass（floor）** =「这项打分至少要达到 X，才算这项过线」。未达 floor 不一定否决整条用例（见 §7.4）。

| 量纲 | 名称 | 我们在测什么 | 单项过线门槛 |
|------|------|--------------|--------------|
| 机会约束满足 | ccp | 行程是否在**安全时间预算内、不超负荷**（过线必须满分） | **1.0**（硬门槛：要么过、要么不过） |
| 调整合理性 | adjust | 用户说缩短/加点/换点/放慢后，路线变化是否**跟请求同向**（首轮无改线时视为满分） | **0.6** |
| 主题相关性 | theme | 停靠是否贴合用户要的旅行主题（文史、亲子等更严） | **0.6**；历史文化游 / 亲子研学游 **0.7** |
| 地理连贯 | geo | 相邻景点之间会不会出现**离谱的远距离跳跃** | **0.6** |
| 停靠密度 | density | 一天停几站是否和可用时间匹配——**别一天只有 1 站，也别塞太满**；亲子半天更克制 | **0.5** |
| 约束保留 | retain | 用户明确的硬要求（半天、亲子、低行动力等）**改完计划后还在不在**；没有硬要求时视为满分 | **0.7** |

综合分权重（产品理解即可）：机会约束 25%、调整合理 20%、主题 20%、地理 15%、密度 10%、约束保留 10%。公式见附录 A。

与 §5 护栏的对应关系：

| 离线量纲 | 主要对应护栏 |
|----------|--------------|
| 机会约束 / 停靠密度 | §5.1 路线可靠性（过满、节奏不合理） |
| 主题相关 | §5.1 无效/主题偏移；§5.2 推荐一致性（可辅以 Judge） |
| 约束保留 / 调整合理 | §5.2 多轮约束保留、未经确认大改 |
| 地理连贯 | §5.1 距离或交通明显不合理 |

### 7.3 综合分「overall 下限」是什么意思

**overall** = 六项按权重加权后的综合质量分。

**overall 下限** = 按用例难度设定的「整条用例综合分至少要到多少，才有资格算 Case Pass」：

| 难度 | overall 下限 | 产品直觉 |
|------|--------------|----------|
| low（简单） | **0.70** | 单主题、轮次少、改线少 |
| medium（中等） | **0.75** | 多轮或少量改线、轻度人格叠加 |
| high（困难） | **0.80** | 多轮多改线、偏好漂移、亲子半天/行动不便等叠加 |

注意：overall 下限是**整案门槛**，不是某一单项的 floor。单项 floor 见上表。

### 7.4 Case Pass vs soft（怎么判定「过」）

**Case Pass（用例通过）** 只看两件事，必须同时满足：

1. **机会约束满足**过硬门槛（满分通过）；
2. **综合分 overall** ≥ 该用例难度对应的 overall 下限（0.70 / 0.75 / 0.80）。

因此：

- 表里的 **Case Pass 200/200（100%）** = 通过数 / 总数，是「整案是否过门禁」。
- 表里的 **CCP / density / theme / … 百分比** = 各量纲**各自过线的比例**，**不等于** Case Pass。
- **soft（软失败）**：整案已经 Case Pass，但某一项（如主题、密度）没达单项过线门槛。报告仍会记下来方便归因，hypothesis 带 `[soft]` 前缀——**不算** Case 失败，不要把它当成「没过线」。
- **硬失败**：整案未过 Case Pass（通常是机会约束不过，或综合分没到难度下限）。

回归建议：盯 Case Pass 与机会约束过线率；用 soft 簇做体验与算法归因。

### 7.5 对话集怎么构成（PM 需知）

| 维度 | 产品含义 |
|------|----------|
| 轮次 | 1–5 轮有效用户输入；首轮必为规划请求 |
| 单人设 / 双人格 / 偏好漂移 | 约束是否冲突、中后轮是否转向 |
| 旅行风格 | 历史文化、自然公园、城市漫游、休闲购物、亲子研学、综合观光等 |
| 改线标签 | 再加点、缩短/半天、换点、累了/下雨/放慢 |
| 难度 | low / medium / high（见 §7.3 门槛） |

金标准强调「硬约束 + 可接受范围」，不锁唯一景点序列。覆盖缺口用少量合成用例补齐（亲子半天、老建筑、雨天换点、行动不便等）。

### 7.6 怎么读多轮摘要报告

`data/eval/reports/multi_turn_summary_*.md` 常见字段：

| 用语 | 含义 |
|------|------|
| 跑次 / 本轮 / 修复前 | 一次完整评测批次；对比标签对应不同时间的报告文件 |
| Case Pass | 整案是否过门禁（§7.4） |
| CCP、density、theme… | 各量纲单项过线率，可 soft 失败而整案仍过 |
| ops tag | 按「缩短 / 加点 / …」切片的 Case Pass |
| difficulty / style_scene | 按难度、旅行场景切片的 Case Pass |
| 硬失败 | 未过 Case Pass 的用例 |
| soft / 含 soft | 整案已过，但单项未过线，用于归因 |

### 7.7 常见 soft / 失败码（产品语言）

| 报告里的码 | 通常对应 | 产品含义 |
|------------|----------|----------|
| 机会约束未满足 | ccp | 行程超出安全时间预算（硬） |
| 主题不够贴 | theme | 景点与用户主题匹配偏弱 |
| 地理跳跃 | geo | 相邻段路程过长偏多 |
| 停靠过稀 | density | 相对可用时间站太少 |
| 停靠过密 | density | 相对可用时间站太多 |
| 硬约束丢失 | retain | 半天 / 亲子 / 低行动力等要求在最终路线上没保住 |
| 改线未生效 | adjust | 用户要改，路线几乎没变 |
| 调整方向不对 | adjust | 有变化，但和请求不同向 |
| 空路线 / 评测异常 | — | 规划器无停靠或跑批出错 |

### 7.8 多 Agent 辅助与人工边界

```text
用户模拟回放对话 → TripSense 规划/改线 → 规则打分（+ 可选文案 Judge）
        → 失败归因聚类 → 人工确认假设 → 开发修复 → 失败子集复测
```

- 用户模拟：按金标准对话回放（或开放生成下一句）。
- 评测 / Judge：规则自动打六项分；大模型 Judge 仅补「理由是否答非所问」等难规则化项。
- 分析：聚类失败原因，提出修改假设。

Agent 评分用于扩大覆盖，**不替代**人工金标准；架构修改必须经人工审核后落地。

### 7.9 场景覆盖方向（持续补充）

在 Eval-200 基础上继续补充：单日与多日、初访与熟客、跨风格多区域、增删换点与跨日移动、雨天/闭馆/预约不足、模糊指代与偏好反转、旅行记录与计划外地点等。

## 8. 时间规则校准

时间风险分为两类：

- **硬风险**：闭馆、预约截止、固定班次、确定的交通不可达；
- **软节奏**：路线可能偏满、连续高强度、绕行较多或缺少休息。

硬风险可以用确定规则判断；软节奏只输出建议，不声称精确预测用户体力。

校准流程：

1. 建立不同天数、区域和旅行节奏的模拟案例；
2. 由人工标注「无需提醒 / 轻提醒 / 需要重排」；
3. 对初始阈值做敏感性分析，观察漏报与误报；
4. 进行小规模可用性测试，关注用户是否觉得提醒频繁、机械或有帮助；
5. 上线后结合确认、忽略、撤销和保存行为迭代策略；
6. 每版策略保留版本和回滚能力。

不直接把「调整 30 分钟且超过行程 1/3」当作可靠定律，它只能作为需要验证的初始假设之一。

## 9. MVP 判断方式

阶段性成功不是「模型生成了路线」，而是同时观察：

- 有足够比例的用户保存路线；
- 保存前对话成本处于可接受范围；
- 用户会再次打开路线并从中继续对话；
- 一部分路线自然产生照片或文字记录；
- 硬约束错误和无效推荐低于可接受阈值；
- 用户没有因机械提醒、登录拦截或隐私担忧大规模流失。

具体目标值需要在原型测试和首批真实数据后设定，现阶段不凭空填写百分比。

## 附录 A：技术实现口径

> 供研发对照；产品读者可跳过。数值必须与 `src/tripsense/eval/metrics.py` 一致。

### A.1 权重与门槛常量

```text
OVERALL_WEIGHTS: ccp 0.25, adjust 0.20, theme 0.20, geo 0.15, density 0.10, retain 0.10
PASS_FLOOR:      ccp 1.0, adjust 0.6, theme 0.6, geo 0.6, density 0.5, retain 0.7
                 （theme：历史文化游 / 亲子研学游 → 0.7）
OVERALL_PASS:    low 0.70, medium 0.75, high 0.80
Case Pass:       ccp.passed 且 overall ≥ OVERALL_PASS[difficulty]
```

### A.2 各量纲自动规则（摘要）

| 量纲 | 规则要点 |
|------|----------|
| ccp | `chance_constraint_satisfied` 且 `planned_minutes ≤ safe_budget_minutes`；满分或 0 |
| adjust | 相对上一轮 + tags：缩短未体现 −0.35；加点 noop −0.3；换点 noop −0.4 等；无 tags → 1.0 |
| theme | 停靠命中 scene/focus/categories 比例 `r`；`s = clip(r/0.5)`；多轮对照首轮话术 / `must_scene` |
| geo | 相邻段 `travel_to_next_minutes > 90` 记异常；`s = 1 - anomalies/n_edges` |
| density | `expected = clip(round(available_minutes/90), 2, 8)`；亲子+半天 `expected ≤ 4`；`s = 1 - min(1, \|n-expected\|/expected)` |
| retain | 半天：`available` 与 `planned` 均 >270 → 罚；低行动力：均段 >55 或停靠 >5 → 罚；亲子空 plan → 罚；无 hard → 1.0 |

### A.3 跑批入口

工作目录为仓库根目录。离线默认不依赖 API Key。

```bash
python -m tripsense.eval --smoke
python -m tripsense.eval --split all --first-turn-only
python -m tripsense.eval --multi-turn --judge stub
python -m tripsense.eval --multi-turn --ids dlg-0003,syn-002
python -m tripsense.eval --multi-turn --llm --limit 20
```

报告：`data/eval/reports/eval_report_*.json`、`multi_turn_summary_*.md`、`attribution_notes_*.md`。

### A.4 失败归因字段

见 `src/tripsense/eval/schema.py` 中 `FailureAttribution`。常用 `failure_codes`：`ccp_violation`、`theme_mismatch`、`geo_jump`、`overcrowded`、`too_sparse`、`constraint_dropped`、`adjust_opposite`、`op_noop`、`intent_parse_miss`。根因分类：`prompt` | `algorithm` | `knowledge_data` | `rag_architecture` | `case_design` | `other`。

### A.5 基线备忘（2026-09-26）

密度选种修复后：首轮 200/200 Case Pass、density ≈ 99%；多轮 200/200 Case Pass、density ≈ 96.5%、theme ≈ 96%；剩余多为 soft（`theme_mismatch` / `too_sparse`）。

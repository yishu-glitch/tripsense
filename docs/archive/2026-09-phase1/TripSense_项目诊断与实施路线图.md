# TripSense 项目诊断与实施路线图

## 结论

TripSense 已经具备清晰的产品个性、完整的六屏体验构想、北京与上海 POI 数据、800 条合成多轮对话，以及一套包含意图解析、场景分类、卡尔曼偏好追踪、CCP/DRCCP 路线优化和局部路线编辑的算法原型。

当前最重要的工作不是继续增加模型复杂度，而是统一产品范围，修正核心算法错误，并把 HTML 原型与 Python 能力接成一个可以真实操作、可以复现实验、可以向他人演示的 Web MVP。

## 现有资产盘点

### 产品定义

- 产品定位明确：根据用户当下状态规划旅行路线，并在时间不足或有余力时给出有个性的动态建议。
- 已定义四种路线模式：悠然漫步、充实全览、深度探索、光影追逐。
- 已定义核心体验：情绪识别、时间滑块、双向提醒、文化卡片、活攻略和 UGC 回流。
- 已定义语气边界，产品人格较完整，可直接转成提示词与文案规范。

### HTML 原型

- 单文件 HTML，包含封面和六个可交互页面。
- 情绪识别使用关键词匹配；路线、景点、提醒和文化卡片均为黄山静态数据。
- 时间滑块、超时提醒、余力加站、文化问答和行程打勾已有前端交互。
- 没有后端请求、数据库、账号、地图或真实算法调用。

### 数据流水线

- 北京原始 POI 8,123 条，上海原始 POI 7,603 条。
- 修复版清洗后，北京 7,976 条，上海 7,509 条；无重复 POI ID、无缺失坐标或热度。
- 北京和上海各有 300 个节点、6,000 条边的距离子图。
- 有 800 条多轮合成对话，城市分布基本均衡；训练集可取前 600 条，验证集取后 200 条。
- 停留时间只有 5 条记录，绝大多数景点仍依赖类别默认值。
- 修复版 POI 增加了父景点、主景点标记和六维内容属性分数，应该作为主数据版本。

### 算法模块

- 意图解析：DeepSeek JSON 输出加规则修正。
- 场景分类：六类旅行场景，支持局部调整识别。
- 偏好追踪：八维状态的卡尔曼滤波与 EM 噪声估计。
- 路线规划：多属性打分、时间机会约束和贪心路线扩展。
- 路线编辑：支持加点、删点、替换、缩短、延长停留和临时休息点。
- 已有离线评估和部分演示结果，但尚无自动化测试、API 服务和前端接入。

## 两个压缩包的关系

以下文件在两个压缩包中内容完全一致：

- `data/dialogue/dialogues.jsonl`
- `data/distance/dist_beijing.json`
- `data/distance/dist_shanghai.json`
- `data/processed/dwell_time.csv`

POI 清洗文件并不相同。`tripsense_fixed.zip` 中的版本经过进一步清洗与特征工程，新增六维属性分数及父子景点字段，应保留为运行时主数据；`tripsense_data_pipeline.zip` 应保留原始数据、采集脚本和可复现的数据生成过程。

推荐整合方式：

- `data_pipeline/` 保存采集、清洗、距离构建和语料生成代码。
- `data/raw/` 保存不可手工编辑的源数据。
- `data/processed/` 保存模型直接消费的版本。
- `tripcore/` 保存意图、场景、偏好、规划和编辑模块。
- 不在多个目录重复保存同一份对话与距离文件。

## 必须先修复的问题

### P0 安全与可运行性

1. `scripts/debug_one.py` 含有明文 API Key。应立即撤销该 Key，清理文件与提交历史，并改用环境变量。
2. POI 爬虫使用 `verify=False` 关闭 HTTPS 证书校验，应恢复证书验证。
3. 项目没有锁定依赖。现有说明只列出部分包，实际运行还依赖 `scipy`、`requests`、`tqdm` 和 `openai` 等。
4. 缺少 `.env.example`、`.gitignore`、统一配置和一键启动方式。

### P0 路线约束公式

当前安全预算使用：

`t_safe = mu - sigma * Phi^-1(epsilon)`

当 `epsilon = 0.1` 时，`Phi^-1(0.1)` 为负数，因此安全预算反而大于平均时间。若目标是使超时概率不超过 `epsilon`，应使用下分位数：

`t_safe = mu + sigma * Phi^-1(epsilon)`

等价写法为：

`t_safe = mu - sigma * Phi^-1(1 - epsilon)`

现有评估也印证了这个问题：`epsilon=0.1` 时平均满足概率只有约 0.644，而不是应达到的约 0.9。修复后需要重跑全部指标，并重新定义 DRCCP 惩罚项的单位和含义。

### P0 上海路线候选错误

`build_poi_graph` 内写死了北京经纬度范围。北京有 5,631 条记录能通过该条件，上海只有热度大于等于 0.99 的 8 条记录能保留，导致上海规划实际上不可用。

应把城市边界作为配置传入，或直接依据距离矩阵的节点集合筛选候选。

### P0 场景和类别没有真正约束候选

`build_poi_graph` 接收 `categories` 参数却没有使用。主流水线也没有在构建候选时传入场景类别，因此“历史文化游”“自然公园游”等场景主要只改变属性权重，不能保证候选类型符合用户要求。

应统一建立“场景类别白名单、次选类别、排除类别、商业场所开关”的候选过滤逻辑，并为候选不足准备回退策略。

### P1 多轮意图识别质量不足

- 规则 Delta 方向匹配率约 79.2%，但非零覆盖率只有约 22.0%。
- 局部调整召回率约 15.7%，全局场景切换召回率约 25.3%。
- 卡尔曼状态协方差持续下降，但真实误差随轮次上升，说明系统在变得更加自信的同时并未更加准确。
- LLM 请求失败时，`parse_intent` 直接返回上一轮参数，当前轮的规则修正不再执行。现有演示结果中已经出现 `Connection error`，但修改类型仍为 `initial` 的情况。

建议先将意图解析改成“本地确定性解析作为基线，LLM 只补充语义”，并把调整类型、时间变化、点名 POI 和场景切换分别评估。

### P1 路线编辑后的距离不一致

替换中间景点后，当前实现没有完整重算前一站到新景点、新景点到后一站的路程；部分场景会沿用旧路线的 `travel_to_next`。因此编辑后的总时长可能与真实路线不一致。

每次增删改后都应运行统一的路线归一化函数：重新编号、重算相邻边、重算总时长、重新检查营业时间和机会约束。

### P1 产品、原型和数据范围不一致

- 产品文档的典型体验与 HTML 原型使用黄山。
- 数据和模型只有北京、上海。
- 产品文档把目的地搜索列为第一屏；HTML 原型省略目的地搜索，另把智能提醒拆成独立页面。

建议第一版 Web MVP 只支持北京，保留黄山原型作为视觉参考。北京闭环完成后再增加上海。这样无需立即补齐黄山数据，也能用现有模型快速上线真实体验。

## 推荐的 MVP 范围

### 用户能完成的主流程

1. 选择北京并描述今天的状态、可用时间和同行情况。
2. 系统返回识别出的旅行场景，并允许用户修正。
3. 系统生成 2 至 5 个 POI 的路线，解释推荐原因、预计停留和移动时间。
4. 用户拖动停留时间，系统实时提示充裕、稍紧、偏满或超时。
5. 用户用自然语言执行加点、删点、替换和缩短行程。
6. 用户保存路线，并在本地记录完成状态。

### 暂不进入第一版

- UGC 公共路线库和社交关系。
- 实时人流、预约余量和天气自动重规划。
- 多人偏好协商。
- 生成式视频、Lottie 和正式账号体系。
- 复杂商业化与景区合作能力。

## 推荐技术架构

### 前端

- React、TypeScript、Vite。
- 将现有 HTML 的视觉语言拆成可维护组件。
- 首版保留浏览器本地存储，用于保存路线和完成状态。
- 地图可在路线逻辑稳定后接入，避免地图工作阻塞核心体验验证。

### 后端

- FastAPI 提供统一 JSON API。
- `tripcore` 作为与 Web 框架无关的纯 Python 包。
- LLM 提供方通过接口封装，支持 DeepSeek 及本地规则降级。
- 首版使用 SQLite；需要地理检索时再迁移 PostgreSQL/PostGIS。

### API 边界

- `POST /api/v1/intent/parse`
- `POST /api/v1/routes/plan`
- `POST /api/v1/routes/{route_id}/edit`
- `PATCH /api/v1/routes/{route_id}/stops/{stop_id}`
- `POST /api/v1/routes/{route_id}/save`
- `GET /api/v1/health`

### 工程质量

- Pydantic 定义全部输入输出结构。
- Pytest 覆盖公式、城市候选、场景过滤和路线编辑。
- 固定随机种子，评估结果记录数据版本和代码版本。
- 使用 `.env` 读取密钥，日志永不输出密钥。
- 加入 `requirements.lock` 或 `pyproject.toml`，提供一键启动脚本。

## 三个实施阶段

### 阶段一 核心可信

- 清理凭证和目录重复。
- 建立统一 Python 包、依赖和测试。
- 修复机会约束符号、上海边界、类别过滤和编辑后距离重算。
- 重跑离线评估，确保指标定义与目标一致。

完成标准：离线测试可一键运行；北京与上海均能产生合理候选；当 `epsilon=0.1` 时经验满足率接近或高于 0.9。

### 阶段二 可演示 Web MVP

- 把 HTML 拆成 React 页面和组件。
- 用 FastAPI 暴露路线规划与编辑能力。
- 接通情绪输入、路线生成、时间滑块、动态提醒和路线保存。
- 增加无 API Key 的本地规则模式，保证演示稳定。

完成标准：新环境按 README 可在十分钟内启动；从输入状态到保存路线的完整流程无需修改代码。

### 阶段三 AI 产品验证

- 招募 5 至 10 名目标用户完成任务测试。
- 记录首次出路线成功率、路线接受率、调整次数、保存率和解释有用度。
- 基于真实交互补充意图数据和停留时间数据。
- 再决定是否投入 UGC、实时数据和移动端。

完成标准：核心体验由真实用户行为验证，而不是只依赖合成数据指标。

## 下一步建议

直接进入阶段一和阶段二的合并冲刺：先用一轮工程重构修复算法与安全问题，再用同一套核心模块接出北京 Web MVP。不要先继续扩充论文式模型，也不要先迁移到 NoCode；现有 Python 资产和单页原型已经足够支撑一个更可信、更完整的作品。

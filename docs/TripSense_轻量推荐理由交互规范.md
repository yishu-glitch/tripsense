# TripSense 轻量推荐理由交互规范

## 1. 设计目标

推荐理由需要回答“为什么是这里、为什么现在去”，但不能挤占路线本身。
默认状态只展示与用户当前需求最相关的一条理由；证据、取舍和替代方案按需展开。

## 2. 信息层级

### 路线级理由

显示在路线标题下方，用一句话解释整条路线的组织逻辑，建议 20—36 个汉字。

示例：`围绕梧桐区串联老建筑与街巷，步行集中，四小时节奏较松。`

### 地点级理由

每张路线卡片在地点名下展示一个“推荐给你”短句，建议 12—22 个汉字，
最多补充两个事实标签。

示例：

- `武康路｜老建筑集中，适合慢走拍照`
- `LV巨轮｜室内展览与建筑打卡，雨天也合适`
- 标签：`步行 8 分钟`、`需预约`

### 展开层

用户点击“为什么推荐”后，才展示：

- 匹配了哪些个人偏好或当下约束；
- 营业时间、预约、天气等可靠依据；
- 为什么排在路线中的这个位置；
- 主要取舍及一个可替换选项。

展开内容控制在 3 条以内，不生成景点介绍长文。

## 3. 卡片交互

默认卡片结构：

`时间段 → 地点名 → 一行推荐理由 → 行程必要标签`

用户拖动时间条或用自然语言提出变化后，AI 只在受影响的卡片旁显示变化说明：

- `为减少折返，已与下一站对调`
- `时间缩短 1 小时，保留你更偏好的建筑路线`
- `下雨后改为室内点，原地点保留为备选`

变化说明应短暂高亮，确认后收起，避免路线页面长期堆积解释。

## 4. 生成机制

推荐理由不应由大模型凭空生成，而采用“事实与决策先确定、语言由 AI 表达”的方式：

1. 结构化数据提供距离、营业时间、类别、预约和场景标签；
2. RAG 提供建筑、文化与体验特征；
3. 路线引擎提供入选原因、排序原因和被舍弃方案；
4. 用户画像与当前对话提供个人偏好及临时状态；
5. 大模型选择最重要的 1—2 个依据，生成自然、克制、因人而异的表达。

建议后端向大模型提供结构化的 `reason_evidence`，输出：

- `route_reason`：整条路线的一句话逻辑；
- `poi_reason_short`：地点卡片短理由；
- `poi_reason_detail`：按需展开的依据；
- `adjustment_reason`：重规划发生了什么、为什么；
- `confidence` 与 `source_refs`：供系统校验，不默认展示给用户。

## 5. 文案约束

- 先说与用户的关系，不先说百科信息；
- 每个地点只保留最有区分度的理由；
- 不重复地点名、评分或用户刚说过的话；
- 不使用“必去、完美、绝对适合”等无依据表达；
- 涉及营业、预约、天气时标记信息更新时间；
- 依据不足时说明不确定性，不补写事实。

## 6. MVP 验收标准

- 用户在不展开详情时，能在 3 秒内理解路线为何这样安排；
- 100% 的理由可以追溯到用户约束、结构化数据、RAG 或路线决策；
- 单张卡片默认理由不超过 22 个汉字，事实标签不超过 2 个；
- 行程调整后，只解释实际发生变化的地点和约束；
- 相同地点面对不同用户或场景，推荐理由能够体现差异。

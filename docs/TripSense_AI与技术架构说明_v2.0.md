# TripSense AI 与技术架构说明 v2.0

> 本文说明模型、路线算法、规则、数据库、RAG 与实时工具如何共同支撑产品体验。

## 1. 总体原则

TripSense 不把大模型限制为“意图分类器”，也不让大模型独自决定事实和路线。系统采用可替换模型的混合架构：

- 大模型负责理解、推理、方案权衡、导游式解释和自然表达；
- 路线算法与规则负责时间、距离、顺序、开放、概率约束和变更影响；
- 数据库负责结构化地点事实；
- RAG 提供历史、文化、建筑与体验知识；
- 实时工具提供天气、预约、拥挤与交通状态。

算法和后端可以进行相对精确的计算；用户侧文案对软性节奏进行自然泛化，只对硬锚点展示精确信息。

## 2. AI 的产品角色

AI 应表现为“导游＋同行伙伴”，而不仅是槽位抽取器。主要职责包括：

1. 从对话和行为中逐步理解旅行目标、兴趣、节奏、避雷项和未表达的取舍；
2. 基于城市知识和候选路线设计多日旅行弧线与每日主题；
3. 比较候选方案，解释为什么选择某片区域、某个地点或某种顺序；
4. 处理“少一个小时”“想加咖啡”“突然下雨”等开放式变化；
5. 在不确定时主动追问，或说明还缺少什么证据；
6. 把算法结果转化为亲和、简洁且符合场景的建议；
7. 长期积累经用户确认的偏好，而不是从单次行为武断推断。

## 3. 上下文分层

### 3.1 长期偏好

跨行程复用的偏好，例如喜欢建筑、愿意慢走、对热门排队敏感。只有多次行为或用户确认后才提高置信度，允许查看、修改和删除。

### 3.2 当前行程上下文

目的地、同行人、天数、可选日期、住宿区域、已选灵感、每日主题、路线版本、锁定内容、预约和开放要求。

### 3.3 当前交互上下文

当前页面、选中的日期/地点、刚刚调整的字段、待确认的方案，以及对话中的指代对象。

### 3.4 临时状态

用户主动提供的当前位置、剩余时间、天气感受、体力和即时想法。默认只在当前会话或用户指定的时段内有效，不自动固化为长期偏好。

每次模型调用只组装完成任务所需的最小上下文，并在界面上让用户知道正在讨论的行程。

## 4. 规划编排

建议流程：

```text
用户输入/交互
  → 语义理解与待确认信息
  → 结构化候选条件
  → 数据库/RAG/实时工具检索
  → 候选 POI 与区域聚类
  → 路线算法生成候选方案
  → 规则校验硬约束
  → 大模型比较、组织与解释
  → 用户确认
  → 保存路线版本与决策依据
```

模型输出采用受约束的结构化协议，至少包含：理解结果、需确认信息、路线操作建议、理由、证据引用、置信度和禁止自动执行的动作。

## 5. 时间调整与触发策略

滚轮滑动过程只做本地预览或轻量计算，不在每个 5 分钟刻度调用大模型。用户结束调整后：

1. 路线引擎重新计算相关日期；
2. 规则检查硬冲突和软性节奏变化；
3. 无重要影响时更新结果，不调用模型；
4. 有明显取舍、需要替代或跨日重排时，调用模型解释并生成选项；
5. 用户确认后写入路线新版本。

阈值由策略配置管理，保留版本号、触发原因和结果日志，不能硬编码成永远正确的真理。

## 6. 知识与数据分层

| 层级 | 内容 | 来源与处理 |
|---|---|---|
| 稳定知识 | 历史、文化、建筑、体验特征、适合人群 | RAG 文档，带来源、更新时间和分块 |
| 结构化状态 | 名称、位置、类型、父子关系、营业时间、入口、评分 | POI 数据库与服务层 |
| 实时状态 | 天气、拥挤、预约、临时闭馆、交通 | 工具/API 调用，带查询时间 |

检索先用城市、类别、空间和硬条件过滤，再用语义召回和重排补充体验信息。生成回答时区分事实、推断和建议。

## 7. 上海 POI 服务层

MVP 仅覆盖上海市内，昆山、太仓、嘉善等周边城市留到二期。

数据治理规则：

- 商场、商业街、书店、咖啡等只要能够构成真实旅行场景即可保留；
- 商场内普通连锁品牌门店不作为独立旅行目的地；
- 企业园区、入口、停车场、厕所、售票处等不进入主推荐；
- 父子关系只表达对检索和游览有价值的真实层级，如园区—馆舍、景区—子景点；
- 入口设施可以作为导航属性，但不作为子景点；
- `full_parent_name_in_address`、`explicit_inside_address`、`geographically_consistent` 等审核字段不作为后端产品语义；
- 场景类型必须面向真实用户需求，例如商场可标为室内休闲，而不是一律视为非景点。

现有高德回填覆盖 5,600 余个真实 ID，补充了图片、营业时间、评分、电话、入口和部分父子信息；费用、出口、历史文化和体验知识仍不足。ID 未返回且明显低价值的企业、普通门店和冷门无效地点优先剔除。

## 8. 实时工具与证据

天气、预约、开放和交通结果需要保存来源、查询时间、适用日期和置信状态。工具失败时不让模型补写事实，而是提供核验入口或说明暂时无法确认。

对于大众点评、美团、百度地图等数据，首先评估开放平台、授权范围和合规性，不以不可持续的抓取作为核心依赖。

## 9. 模型无关与评测

DeepSeek 是当前意图解析入口，但架构不能绑定单一模型。不同模型共享：

- 相同输入上下文与工具权限；
- 相同结构化输出协议；
- 相同离线场景、事实核验和路线质量标准；
- 统一记录成本、延迟、失败率和用户行为结果。

现有约 800 条模拟多轮对话可用于覆盖和回归，但不能证明真实产品效果。后续多 Agent 研发流程可包括：场景生成 Agent、执行/验收 Agent、结构化分析与修正建议 Agent；架构修改仍需人工评审，避免自动闭环放大错误。

## 10. 照片与隐私

照片文件存储于用户私有对象存储，业务数据库只保存文件标识、用户、行程、地点、时间、说明和权限。默认去除或隐藏 EXIF 精确位置；AI 读取需要单独授权；用户数据默认不用于训练；删除操作同步清理对象和关联记录。

## 11. 可运行 MVP 的本地闭环

当前 MVP 使用单进程 FastAPI、SQLite 和静态原型组成可复现闭环：

```text
浏览器原型
  → FastAPI 路线、行程、记录、日记接口
  → JourneyStore / SQLite
  → 本地确定性路线规划器与日记模板生成器
```

- 浏览器与 API 使用同源地址，保存行程、记录旅途和生成日记均可真实持久化；
- 自定义心情、计划外地点和照片引用属于旅途记录，不反写成长期偏好；
- 没有旅途记录时拒绝生成空日记；每次生成保存一个新版本，并记录来源记录数；
- 日记生成器当前标记为 `local-template-v1`，用于无凭证 demo 和自动化回归；
- 后续接入大模型时，应保持同一日记响应协议，并将提示词、模型版本、来源记录版本和安全审核结果写入生成元数据。

本地闭环不实现账号鉴权、照片二进制上传、多人共享和云部署。这些能力需要明确身份体系、对象存储、隐私策略和供应商后再进入生产实现，不能以本地 demo 的默认值代替产品决策。
